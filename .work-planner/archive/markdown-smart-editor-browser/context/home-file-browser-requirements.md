# 首页文件目录交互需求

## 用户目标

在现有首页文件浏览器中增强目录的可扫读性和文件移动效率：

1. 文件夹始终组成列表上半部分，Markdown 文件组成下半部分。
2. 文件夹组与文件组分别按最近更新时间降序排列，最近更新的条目在前。
3. 单个 Markdown 文件可拖放到当前列表中可见的文件夹内完成移动。
4. 拖放只用于移动文件，不提供手动拖放排序，也不允许拖动文件夹。

## 语义约定

- 文件更新时间使用文件系统的 `contentModificationDate`。
- 文件夹的“有效更新时间”取其全部后代可见 Markdown 文件中最新的修改时间，包含嵌套子目录。
- 空文件夹或没有任何后代 Markdown 文件的文件夹，回退到目录自身的 `contentModificationDate`。
- 同组更新时间相同时，使用本地化自然名称升序作为稳定次级排序键，避免列表反复抖动。
- 系统 `Inbox`、隐藏条目与非 Markdown 文件继续排除，不参与文件夹有效更新时间计算。

## 拖放边界

- 触控使用 Apple 系统拖放手势：按住文件行直到拖动预览浮起，再拖到目标文件夹；不自定义长按计时或另设“排序模式”。
- 使用 SwiftUI/UIKit 系统拖放 API 提供标准拖动预览、取消、放置提案和指针行为，同时保持普通轻点仍然打开文件。
- 仅 `DocumentNode.Kind.markdown` 产生 App 内拖放载荷。
- 仅文件夹行接收载荷；文件行不成为放置目标，列表不接入 `onMove` 或拖放重排。
- 放到文件当前所在目录视为无操作；移动失败时原文件必须保留并显示现有错误反馈。
- 重名沿用 `FileStore.move` 的自动序号策略。
- 保留现有“移动”面板作为向上级目录移动、辅助功能操作和拖放不可用场景的完整入口。

## 验收重点

- iPhone/iPad 的系统按住拖动，以及 iPad 指针场景均能稳定触发，不与 `NavigationLink` 轻点进入文件/文件夹冲突。
- 文件悬停在合法文件夹上时有清晰但不过度的视觉反馈；取消拖放不改变磁盘或列表。
- 移动成功后源目录立即刷新，目标目录打开后可见该文件；排序按新的有效更新时间重新计算。
- 深层目录、大量文件、同时间戳、空目录与移动失败场景均有覆盖。

## S10.3 首轮设备反馈（2026-08-11）

- 长按文件后拖到文件夹没有成功完成移动，S9 的系统拖动源/放置目标组合必须重新验证。
- 新增的整行 `listRowBackground` 覆盖了原有 List 行背景行为，导致向左滑动 item 时原有圆角消失。
- 修复必须先恢复原有列表与 swipe actions 的系统视觉，不得为了 targeted 高亮改写整行背景。
- 除上述已知问题外，需要审计 Browser 本次 diff，排除点击、滑动、导航、行布局和主题样式的其它非需求改动。

## S10.3 第二轮设备反馈（2026-08-11）

- 文件长按后能显示系统拖动预览，证明 drag source 已生效。
- 在文件夹上松手后预览回弹，源文件仍在原位，目标文件夹内无新文件；失败点收窄到 List 子行 drop destination 未接受操作。
- 不再在 `List` 子行上挂 `dropDestination` / `onDrop`；改为 List 级单一放置目标，再按 drop 坐标命中可见文件夹行。
- 继续保留原生 `List` 和 `swipeActions`，不为规避系统 drop 问题改成自定义列表。

## 最终产品决定（2026-08-11）

- List 级放置目标方案在真机上仍未成功移动文件，用户明确要求移除拖拽功能。
- 删除所有 drag/drop API、载荷、目标高亮、行几何测量、专用存储校验与测试，不保留隐藏实现。
- 保留 S8 的文件夹/文件分组与最近活动排序；文件移动仅通过原有左滑“移动”面板完成。
