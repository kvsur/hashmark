# AI Provider 模型治理需求（2026-08-25）

## 原始任务

系统优化所有 AI Provider 的模型发现、能力判断、配置保存和后续维护机制。

核心前提：后续不依赖自建 CDN 或 Server API，因此方案必须优先利用 Provider 官方 models API、App 内置声明式 Manifest、模型家族规则、运行时能力验证和本地缓存。

主要目标：

1. 刷新后获取的最新模型必须能够稳定选择和保存，重新进入设置不能回退到旧默认模型。
2. 删除散落在 Swift 代码里的逐型号硬编码，模型清单、家族、能力、弃用状态应收敛成可验证、版本化的声明式配置。
3. 能力判断采用分层机制：Provider 返回的元数据 > 精确例外 > 家族规则 > 已验证的本地结果 > 未验证的保守降级。
4. 图片、PDF、通用附件、推理、原生 Web Search 等能力分别判断，不能因为模型未被本地认识就一律判为不支持。
5. 用户开启 Web Search 后，支持该协议的 Provider 应直接发送原生搜索配置，不能依赖“搜索、最新、股价、行情”等关键词。
6. 未知新模型允许显示、选择、保存和文本调用，并明确标记“能力未验证”。
7. 增加自动化差异检查和测试，便于后续发现 Provider 新增、改名或下架模型。
8. 明确哪些变化可由本地数据/运行时适配，哪些协议变化仍必须发版。

开始时先审阅现有 Provider、模型目录、能力规则和设置持久化实现，确认当前工作树已有改动，形成分阶段实施方案，再按阶段实现并验证。遵守 AGENTS.md，保留用户已有修改，不要提交。

## 后续硬约束（2026-08-25）

- 一定要保证现有的能力不能被破坏。
- 该约束解释为 App 改造零回归：当前六家已经通过离线契约验证的文本、流式、推理、原生搜索、图片、PDF、普通文件、上传/提取/检索、引用/续传和设置恢复能力必须全部保留。
- 若 Provider 上游真实下线或改变协议，不能伪装仍可用；应阻断本阶段交付并明确报告，不得把上游变化或能力删除静默混入本重构。
